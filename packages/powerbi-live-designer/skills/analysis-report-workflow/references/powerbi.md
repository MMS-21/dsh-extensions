# Power BI adapter

## Choose the report and operation

Start Power BI Live Designer using `pbi_start_task` with the intended mode. For a new report, ask the user to save a new Power BI Project (.pbip) in Power BI Desktop and paste the full path into chat. For an existing report, ask them to open its .pbip and paste the full path. Confirm the target using `pbi_start_task` with the same mode and exact path before any connection, design or authoring tool. A source file or a report name alone is insufficient. Use a separate chat for a different project.

- **Refresh data in an existing open report:** Call `pbi_connect_open_report` with the confirmed project to list its live tables. Use `pbi_refresh_data` for the table scope the user requested. If the scope is unclear, use the table list to ask which tables to refresh. Report the completed tables and observed row counts separately from any visual or KPI checks. Go straight to the confirmed report and selected tables. If the direct connection fails, report the exact blocker and offer **Home → Refresh** in the confirmed Desktop report. After an interrupted refresh, inspect Desktop before a retry.
- **Plan a new report or redesign:** Start the brief and page plan from the confirmed target and available source metadata. Continue planning in chat if the report editing connection is unavailable. Save the design plan through the plugin once connected and before staging file changes.

## Connect for controlled authoring

1. When you are ready to edit report files, use `pbi_configure` with the confirmed PBIP path and configured local service address, then `pbi_check_connection`. If the connection fails, tell the user which report editing action is unavailable and continue with the design plan in chat. For a PBIX, ask the user to save a separate PBIP copy in Desktop.
2. Use `pbi_inspect_semantic_model`. This reads disk metadata only, without rows, DAX/M execution, refresh, or model edits. TMDL inspection is partial and cannot establish measure meanings, complete types/hierarchies, or runtime filter behavior. Remote models and unsupported formats must be reported, not guessed. Unsaved Desktop state may differ from disk.
3. Use `pbi_plan_design` to persist the proposed brief and design. It writes a planning record, not Power BI report files. Use the returned plan id in `pbi_record_review` to retain the user's feedback or an evidence-based finding. State whether feedback is user-provided or an agent finding; recording it is not approval to execute a mutation.
4. Use `pbi_get_operation_log` to surface recent outcomes and journal file locations. An unfinished started entry or timeout is unresolved. Read captureEvidence: a warm screenshot does not prove that on-disk changes were loaded; wrong-page results are rejected and identical images across pages are flagged unverified. A render error alone does not establish a Desktop crash or an unsupported visual type. The host journal also covers unreachable-service attempts. Screenshots are optional verification evidence, not an embedded live report. `pbi_capture_page` requires a reachable, matching project; `pbi_get_artifact` supplies the captured file for visual inspection.


Use `pbi_validate_project` for read-only authoring-CLI validation. Keep that result distinct from `pbi_check_connection`: Desktop readiness does not mean schema validation passed, and validation failure does not mean Desktop is inaccessible. Report missing `$schema` diagnostics as formal validation findings, not as proof that a Desktop-saved project cannot open. Microsoft's [PBIP schema](https://github.com/microsoft/json-schemas/blob/main/fabric/pbip/pbipProperties/1.0.0/schema.json) and [report definition schema](https://github.com/microsoft/json-schemas/blob/main/fabric/item/report/definitionProperties/2.0.0/schema.json) require `$schema`; do not suppress the diagnostic or bypass a reload guard. Schema-fetch warnings mean coverage is incomplete, not that the underlying files are invalid. Never add guessed schema URLs or edit the project merely to make a check green.

New operation events identify specific Desktop actions, safe diagnostic codes and external dispatch state. For older entries without those fields, report the detail as unknown; a generic RuntimeError or absent successful write does not establish that no write was attempted.

## DSH-authored file changes

DSH chooses and authors the report/model definitions using the design skills. Use pbi_stage_changes with the saved design plan, explicit relative paths, proposed text and current beforeSha256 checksums. Stage CSV import definitions only as proposed model files; this does not run the import. The plugin never generates business-specific visuals or models for the agent. Bind fields using the real table entity (`SourceRef.Entity`) and property; do not treat a table name as an undeclared query-source alias. Schema validation is separate from runtime binding and rendering.

Use `pbi_validate_changes` on the isolated copy. For actual edits, direct the user to **Power BI Live Designer → Change review → Review pending changes → Approve these changes** to inspect and approve the diff. The sidebar binds approval to the exact digest. This also authorizes routine refresh and verification against those applied model/source definitions. Design feedback and review findings do not authorize file execution. Then `pbi_apply_changes` can checkpoint and apply that exact validated version. Changed project/session, source files or staged content invalidate approval. Route data-only requests with unchanged definitions to the direct refresh workflow.

Use pbi_reload_changes only after application. This rechecks Desktop unsaved state and reloads report/model definitions, not data. Capture optional evidence separately; analytical and accessibility checks remain explicit tasks. On a timeout, inspect state and journal; never blindly repeat reload. The user can use /pbi rollback ID SHA256 to restore unchanged checkpointed files, but that does not undo Desktop's in-memory state. Report partial/unknown outcomes and stop dependent work.

## Verified refresh after controlled authoring

After an approved change set is applied and `pbi_reload_changes` reports `reloadOutcome: succeeded`, use `pbi_stage_model_refresh`. Provide its changeSetId, affected table names, one expected row-count range per table, local sourceFiles with current SHA-256 hashes, and a sourceSummary describing every configured source. Use an empty sourceFiles list only when no local source files are involved; identify remote source freshness as unverified. Inspect the actual model sources rather than guessing from file names. Include dependent tables explicitly when their data must also refresh. The adapter performs table Full refreshes; it never falls back to refreshing the whole model.

Staging reads live metadata and fingerprints the Desktop process, database and complete exported model. It does not process data. Routine refresh inherits task authorization from the same session's approved, applied and successfully reloaded change set. The adapter binds the exact current PBIP path and its child model process, even when window titles are duplicated. Once staging returns `status: ready`, call `pbi_run_model_refresh` with the returned id and digest without asking the user to approve refresh again. Keep the table list, sources and expected row counts in the journal; summarize results to the user. The parent authorization and unchanged model/source fingerprints are rechecked before execution. A new source or changed model definition belongs in a new reviewed change set; it cannot be smuggled into a routine refresh. `/pbi refresh-approve` remains a compatibility command and is never required for this path.

Use `pbi_get_model_refresh` to inspect progress and persisted outcomes. `verified` means named table refreshes completed and their row counts matched the reviewed ranges. Check `canvasReloadOutcome` and `postCanvasVerification`: the refresh workflow also redraws the report layout and verifies that the data survived. Do not declare the report finished before inspecting the captured page. A repeated successful definition reload is a no-op; do not keep issuing reloads to diagnose a blank report. It does not establish correct measures, business totals, source freshness, or visual appearance. Review those independently and capture optional visual evidence. Do not reload model definitions after a successful refresh merely to redraw the canvas; that is a different operation and can discard runtime state. Do not claim the project has been saved automatically.

On `verification-failed`, report observed counts and the tables that completed; do not repeat refresh automatically. On `unknown` or interrupted `running`, inspect the journal and Desktop state. The same instance is blocked from another refresh until the user has inspected it and restarted Desktop. Completed table refreshes may have changed rows even if a later table failed. File rollback restores definition files only; it cannot restore prior engine data. A new Desktop instance requires a newly staged refresh under the still-valid parent task authorization; no separate refresh approval is required. Stop at connection, credential, source, or timeout failures with the exact observed blocker; never request credentials in tool arguments or log them.

In chat, describe connection failures in terms of the affected report action and what the user can do next. Keep implementation details in diagnostic logs.
