# Submit generated Power BI definitions from disk

Prefer this route for multi-page reports. Generate the definition files and a
JSON draft manifest in the session workspace, the prepared project directory
(use a separate staging subdirectory), or the task directory reported by
`pbi_task_status`. Do not overwrite live definitions to create the draft.
Do not print/escape/retype entire generated files into the model conversation.

Then call:

```json
{"manifestPath":"D:/Reports/staging/draft.json"}
```

This is the input to `pbi_prepare_draft`, not a shell command. The path above is
illustrative; use the actual task's authorized output location. The existing
five-tool interface, chat questions and design skills are unchanged.

A minimal manifest has the same fields as an inline draft:

```json
{
  "plan": {
    "audience": "Operations managers",
    "questions": ["What changed in the reporting period?"],
    "pages": [{
      "title": "Overview",
      "visuals": [{
        "question": "What changed in the reporting period?",
        "measure": "Use the verified measure from the prepared model",
        "dimension": "Use the verified period grain",
        "acceptance": "Reconcile the displayed value with the reference query"
      }]
    }]
  },
  "changes": {
    "summary": "Add generated overview page",
    "files": [{
      "path": "Report.Report/definition/pages/overview/page.json",
      "contentPath": "generated/page.json",
      "beforeSha256": null
    }]
  },
  "pages": ["overview"],
  "acceptance": ["The rendered overview reconciles with the reference query"]
}
```

The names and acceptance check are illustrative; use actual model bindings and
page IDs. The referenced file must contain the generated definition itself.

- `path` is the target relative to the prepared PBIP's directory. Backend rules
  still restrict changes to the bound project's supported definition files.
- `contentPath` points to UTF-8 definition text. Relative paths resolve beside
  the manifest. For an inline draft with file references, they resolve in the
  session workspace (project directory if no workspace service exists).
- Supply exactly one of `content` or `contentPath` per file. Inline content remains
  supported. An optional `contentSha256` pins generated bytes before reading.
- `beforeSha256` remains mandatory: the current target's SHA-256, or `null` only
  for a new file. Never guess a hash. Backend checks still reject stale targets.
- Include `checks` for numerical acceptance; model edits require them. Include
  the existing `refresh` object when affected tables must be processed. Their
  schemas match the inline tool and are checked before staging.
- Correct an existing draft with its current digest in `revisionOf`, either in
  the manifest or beside `manifestPath`. Conflicting digests are rejected.
- Do not mix `manifestPath` with inline plan/changes/pages. All user questions
  remain in chat; no sidebar approval is needed.

Local limits: 2 MB manifest, 200 files, 250 KB per definition and 1.5 MB total
content, plus the coordinator's serialized-request budget. Symlinks/junctions,
escaping inputs, duplicate targets, malformed UTF-8 and mismatched content hashes
are rejected. The plugin reads each source once; its captured strings are the
ones staged and validated. Changing source files afterward cannot alter the
prepared change set. Submit a revision to use changed generated content.

The compact `draftSource` receipt persists its manifest hash, source path, file
count and byte count. Recovery does not depend on regenerating or retyping files.
Continue with `pbi_execute_task`; after interruptions inspect `pbi_task_status`
and reconcile known outcomes before replaying any mutation.

This reduces large model-generated tool arguments; it does not change an upstream
provider's idle timeout or guarantee that provider outages disappear.
